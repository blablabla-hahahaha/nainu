# Agent Note 实例（implemented + proposed）

---

## 例 A：implemented（已交付，现在时）
```markdown
# Agent Note: 文档结构、层级与预算
Status: implemented
## Problem
常驻文档累积了重复规则、复述事故、重复包地图与过时的 Agent Note 摘要，
而现有写作指导并没有阻止这种增长。因为仅靠评审无法阻止，仓库需要一个
机械预算伴随其文档分类体系。
## Decision
- **结构跟随文档树**：文档标准规定——一篇文档拥有其主题的细节，只概述
  直接子级的目的/职责/高层行为，并链接到更深的所有者。
- **带「一个事实一个家」的层级分类法**：标准给每个 Markdown 层级分配一个
  职责，禁止在家的层级之外复述事实，并携带写作/评审任何文档时的 slop 清单。
- **一条产品上手路径**：根 README 拥有推荐的包运行路径、源码运行替代与
  紧凑的插件安装用法。
- **一个窄的、硬的预算门禁**：清单里每个文档必须在其词数上限之下；清单
  里有但文件缺失 = 失败（防止重命名悄悄孤立预算）。
- **上限是棘轮收紧的执行前沿**：低于目标保留至少 5% 冗余、上限下移；
  高于目标冻结上限直到降回目标以下。
- **一个薄的工作流技能，契约在文档里**。
## Alternatives considered
- **只靠技能与评审纪律、没有门禁** —— 否决：上文描述的增长在「现状规则 +
  评审者关注」都已存在时仍发生了；一条没有机械兜底的散文规则在这里被
  证明守不住，而本仓库自己的「质量门禁」立场说：值得保留的不变量值得编码。
- **给每个文档层一个宽门禁** —— 否决：一刀切上限惩罚了「长而正确」的文档，
  并制造逐文件豁免的 churn。
- **把标准塞进技能里** —— 否决：契约住在文档、工作流住在技能；塞进
  SKILL.md 的标准对「不调用技能就编辑文档」的智能体不可见。
## Consequences
- 给有预算的文档加内容需要「置换」：搬到分类家并留指针，或精简现有散文。
- 结构性评审先看所有权与文档形式，再做句子级编辑。
- 词数是刻意接受的粗糙代理：它无法判断质量，但它恰好在「作者有上下文
  去正确放置内容」的那一刻强制做「搬迁」决定。
```

## 例 B：proposed（提案，将来时）
```markdown
# Agent Note: 面向受众的文档质量标准
Status: proposed
## Problem
文档系统有很强的放置、新鲜度、链接、双语与源码等价检查，但它没有把
「brief/intuitive/friendly」定义为可评审的读者结果。（……）
## Proposal
采纳一份面向受众的质量契约，含五个定义：Brief（公共路径只含所需事实）、
Intuitive（前置在前、一个明显下一步）、Friendly（能识别成功、理解风险、
从失败恢复）、Accurate（每个持久声明有一个所有者 + 相称的验证路径）、
Agent-readable（元数据/标题/锚点/术语/状态支持定向检索）。
## Alternatives considered
**给每个文档一个统一词数上限。** 否决，因为穷尽参考行、公开契约与决策
依据可以又长又正确。
## Acceptance criteria
- 一份规范质量参考按文档职责定义 brief/intuitive/friendly/accurate/agent-readable。
- （……可观察的完成状态……）
## Risks
- 元数据可能变样板；硬句子限制可能打碎解释或分离条件与后果。
- （……可能出错之处 + 有意放弃的东西……）
```

## 结构点评（生成时对照）
1. **implemented note 用 `## Decision` + `## Consequences`，全文现在时**——描述「是什么」，不是「我们做了啥」。
2. **proposed note 用 `## Proposal` + `## Acceptance criteria` + `## Risks`，可将来时**——描述「要做什么」与「怎样算完成」。
3. **`## Alternatives considered` 每个备选一个加粗引导段落**，写明「否决」及原因。
4. 每个 note 是三件套（`.md` + `.zh.md` + `.i18n.yaml`）；`.i18n.yaml` 记录两侧 blob hash。
