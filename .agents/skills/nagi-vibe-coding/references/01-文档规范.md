# 文档规范（层级分类法 + 词数预算 + slop 清单）

---

## 1. 文档结构
这些规则作用于人类可读文档；Agent Notes（决策记录）在其范围之外。
- 一篇文档的主题与树位置固定其范围：只以适当粒度描述自己的主题，对直接子级只描述**目的、职责、高层行为**，低层细节链接到归属后代。文档类型不扩大该范围。
- 每篇文档分类为 **tutorial（教程）** 或 **reference（参考）**。教程沿有序路径走向一个结果、只引入每步所需；参考定义一个查找范围与当前行为、无教学顺序。substantial 的教程与参考内容要分开；任一部分较小时标注。
- 写教程前先私下把读者起点知识与每个概念分级为 beginner / intermediate / advanced。前置概念在前、难度渐进、多余的高级内容移到后面的教程或参考。
- **写作顺序**：定位文档 → 设定允许粒度 → 选教程或参考 →（教程则按前置与难度排序概念）→ 搬迁后代拥有的细节 → 用链接替换低层解释。
## 2. 层级分类法：一个事实一个家
**核心原则：每个事实只有一个家——职责匹配的那一层；别处用链接指过去。**
下面是 DSH 的层级表（**作为「例」**——映射到你项目的文档树时，把每行的「层」换成你的文档层级，但「职责」与「不该出现」的区分逻辑照抄）：
| 层（例：DSH） | 职责 | 不该出现在这里 |
|---|---|---|
| 根 `AGENTS.md` | 常驻命令：智能体每个会话都需要在上下文的规则，每条 1–3 行并链接其家 | 故事、演练示例、情境流程、从链接的家复述的内容 |
| 子树 `AGENTS.md` | 该子树特有的命令 | 根文件已承载的仓库级规则 |
| `architecture.md` | 有序地图：组合、核心模块、循环、接缝、扩展点；改核心目录前必读 | 类型定义、逐模块细节、决策依据、实现状态标注 |
| `subsystems/`（或等价） | 每个子系统一页参考：类型定义、语义 | 行为叙述 |
| Agent Notes（`.agents/notes/`） | 活跃决策记录：为什么、放弃了什么、必需验证；`implemented/` 以现在时描述已交付现实 | 迁移计划、验收清单、已交付后的 spec-speak |
| `postmortem/`（事故复盘） | 事故故事——唯一允许「战争故事式叙述」的层 | — |
| `cookbook/`（实操手册） | 带编号验证步骤的分步 how-to | 设计依据（→ 指南链接的 Agent Note） |
| 包/模块 README | 逐模块契约：config、语义、限制、扩展点 | JSDoc 复述、生成目录复述、别的模块的事 |
| 生成的参考 | 从源码再生成并做新鲜度门禁的穷尽源 | 手改生成的源 |
| Skills（`.agents/skills/`） | 可复用工作流与专项决策标准 | 产品与运行时契约（→ 文档或源码） |
**放置口诀**：bug → postmortem；依据 → Agent Notes；流程 → cookbook；类型定义 → subsystems；模块契约 → README；常驻命令 → 根 `AGENTS.md` + 依据链接。
## 3. 写作规则
- **只写当前状态，不写变更历史**。持久散文里避免 "previously/now/no longer"、PR、commit、stack 位置；命名现行机制。变更故事放进 commit、PR、Agent Note 或 postmortem（后两者可引已合并 PR/issue 为证据）。
- **每个非平凡变更同 PR 至少附一份 Agent Note**（更新拥有该决策的 note 或新增；只有纯机械/局部编辑豁免）。
- **一段一行**：编辑器软换行。代码块、表格、列表结构保持原格式。
- **围栏代码块必须能编译/校验**：文档里的代码要么真的可运行、要么用「源码等价」围栏 + manifest 注册，保证不漂移。
- **重塑了某文档化类型的同一变更要更新归属页**：机械检查抓「漂移的粘贴」，但要靠流程抓「从未文档化的新类型」。
- **成对同步更新**（若双语）：术语引导、单次通过；重定位首现标注、保留未动散文、重录一致性记录。
- **评论与 JSDoc 陈述完整契约，而非推理过程**：保留行为、失败、时序、所有权、情态、异常、后果、非显而易见取向；删除叙述、测试走查、评审分析、代码复述。保留本地契约 + 链接其依据。
- **写直接点**：点名主体与事实；用确切的名字替代隐喻性的 "gate"、"vocabulary"、"surface"（除非它们精确命名技术主体）。
## 4. 词数预算
- 给「容易膨胀的常驻文档」（根 `AGENTS.md`、`architecture.md`、子树 `AGENTS.md`、包 README 等）设词数上限，用脚本强制。
- 门禁变红时按序：1) **搬迁**属于别层的内容（留一行链接）；2) **精简**属这里但能更短的内容；3) 只有词确实需要空间才**提高**上限（在 PR 里说明理由）。上限过低是预算 bug。
- **上限是护栏，不是削减目标**：低于目标保留至少 5% 冗余；高于目标冻结上限、禁止增长直到降回目标以下；只有仍有空间才降低上限。
- 例（DSH 的预算数字，替换为你的）：根 `AGENTS.md` ≤ 1,950 词；`architecture.md` ≤ 2,400；子树 `AGENTS.md` ≤ 600（`packages/AGENTS.md` ≤ 675、`docs/AGENTS.md` ≤ 1,320）；`packages/README.md` ≤ 994；等等。参考文档、Agent Notes、模块 README 不受预算——长度在那里合法，由评审 + slop 清单治理。
## 5. slop 清单（任何文档审查都要猎杀）
- 同一规则出现在不止一个家（grep 特征短语，留一个家其余链接）。
- 叙述历史或战争故事（"previously/now/no longer/used to/renamed/was moved/PR/commit"）。
- 散文或图中的实现状态标注（"implemented!" / "future: …"）——状态会腐烂，仓库布局与清单才是权威。
- 手写复述的目录、JSDoc、测试/模块/状态清单（源码或生成器才是权威）。
- 推理过程（逐步实现叙述、证明显而易见的分支、测试走查、被否决的局部备选）——保留结果契约或持久依据，删除推导路径。
- 兄弟方法旁重复的依据（应在归属能力/helper 处写一次）。
- 段落墙（一段塞好几条规则 + 括号补充）——拆分或降级细节到其家。
- 强调通胀（到处 bold/CAPS/"critically" = 什么都突出不了）——强调只留给「改变行为的那句」。
- `implemented/` Agent Note 里的 spec-speak（"should"、迁移计划、验收清单）——implemented note 描述「是什么」。
## 6. 交叉引用
- 用**相对 Markdown 路径**链接仓库引用，绝不用裸文件名或 note 编号；`verify-md-links` 拒绝缺失目标与死 `#fragment` 锚点。
---
## 可迁移要点
1. 「一个事实一个家 + 链接」是整套文档治理的根基。
2. 层级表里「职责 / 不该出现」的区分逻辑比具体层级名更重要——**映射层级名，照抄区分逻辑**。
3. 词数预算 + slop 清单 + 交叉引用，三条都要有机械门禁（见 `08-机械门禁模式.md`）。
