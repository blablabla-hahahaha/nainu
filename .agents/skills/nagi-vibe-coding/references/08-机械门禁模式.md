# 机械门禁模式（执行与校验层）

---

## 1. 核心信条
> **值得保留的不变量，就值得编码成可执行的校验脚本。** 纯文字规范 + 无人强制 = 会腐烂。
这是整套 vibe coding 不腐烂的关键。一条规则如果无法接上脚本，就降级为「评审约定」并明确标注，不要伪装成「门禁」。
## 2. 总体形态
```
scripts/verify-*.ts            # 每个脚本验证一条不变量
scripts/<结构真源>.ts          # 结构真源（如 agent-note-tree 的封闭类别集合）
scripts/<预算>.manifest.json   # 预算清单（如 doc-budgets）
scripts/run-gates.ts           # 门禁调度器：依赖图 + 并发 + 模式
lefthook.yml                   # pre-commit / pre-push 钩子
.github/workflows/ci.yml       # CI 编排（穷尽覆盖 + 平台矩阵）
```
## 3. 门禁调度器（run-gates 模式）
一个**「有依赖图的门禁调度器」**，自身不写测试逻辑，只编排已存在的命令：
- 每个 gate 声明：唯一 `id`、`label`、`command` + `args`、`needs`（依赖的 gate，须先 passed）、`after`（须先结算、无论成败）、`env`、`allowFailure`、`streamOutput`。
- 调度器按拓扑顺序并发执行（有并发上限）、跳过依赖失败的 gate、并**校验依赖图无环**。
- 暴露聚合命令（Mode）：如 `doc-sync`（所有文档门禁）、`hygiene`、`ci-primary`、`check-all`；`doc-quick` 是「免构建的快速检查」只跑轻量叶子。
- 关键：**它编排命令，不复制逻辑**；每个 `verify-*` 才是真正干活的。
## 4. 每条门禁都要有「非法用例」
> 强承诺需要「一个有效 fixture + 一个非法 fixture」，证明顶层门禁能失败。
关键心智不是「门禁跑绿了」，而是**「引入该回归会变红」**——每条 `verify-*` 的配套 `.spec.ts` 就是干这个的。
## 5. 钩子策略（刻意做窄）
- **pre-commit**：只做 lint 修复 + 空白检查 + 元数据守卫（快、无副作用）。
- **pre-push**：只跑增量类型检查。
- **绝不**在钩子里跑测试/快照/文档检查/构建/hygiene。
**原则**：钩子做窄，CI 做全。本地只跑与改动相关的**最窄**检查一次；穷尽覆盖、构建产物冒烟、平台矩阵留给 CI。不要手动重复一条已通过的检查。
## 6. 起步建议（先接 3～5 条）
| 规则 | 门禁 | 非法用例 |
|---|---|---|
| 一段一行 | `verify-md-wrap` | 一个多行段落的文档 |
| 相对链接不死链 | `verify-md-links` | 一个死链/坏锚点 |
| Agent Note 骨架正确 | `verify-agent-note-format` | 一份缺 `## Alternatives considered` 的 note |
| 文档不超词数预算 | `verify-doc-budgets` | 一份超限文档 |
| TODO 分级 | lint 规则 | 一个裸 `TODO` 无分级说明 |
## 7. 结构真源与门禁同源
`agent-note-tree` 这类文件**同时是「封闭集合」的结构真源 + 门禁实现**：README 里的「分类」表与脚本必须同步改。这保证「文档说的」和「机器强制」是同一份事实。
---
## 可迁移要点
1. **一条规则 → 一条 `verify-*` → 一个 `run-gates` 聚合里的 gate**。写规则时就问「这条能不能接脚本」。
2. **每个验证脚本都要有合法 + 非法两个 fixture**。
3. **钩子做窄，CI 做全**；本地跑最窄相关检查。
4. 生成目录（如 API 目录）用「确定性再生成 + 比对」做**新鲜度门禁**，手改生成的源会被拒绝。
