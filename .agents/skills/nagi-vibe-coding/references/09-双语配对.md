# 双语文档配对（i18n）

---

## 1. 配对契约
- **两种语言同等权威**：文档可用任一语言先创作与评审；对侧由它翻译。两个文件无主次，绑定它们的唯一约束是「必须说同一件事」。
- **一对 = 三个兄弟文件**：`foo.md` + `foo.zh.md`（目标语言后缀）+ 一致性记录 `foo.i18n.yaml`，同一目录。无 locale 目录、无独立翻译仓库、无双语交错单文件。**成对整体合并**：一个 PR 绝不只落一种语言。
- **一致性记录**：`foo.i18n.yaml` 存两侧的完整 git blob hash（`git hash-object` 结果，非 commit hash）：
  ```yaml
  foo.md: 3f786850e387550fdab836ed7e6dc881de23001b
  foo.zh.md: 89e6c98d92887913cadf06b2adb97f26cde4849b
  ```
  记录哈希能恢复两侧「上次确认一致」的精确文本，所以失配的对是「按编辑侧 diff 最小修补对侧」更新，**绝不整篇重译**。`--write` 重录两侧哈希；那个 yaml diff 就是「我确认这两个说了同一件事」的可评审陈述。
- **语言切换行**：目标语言文件 H1 后紧跟 `[English](foo.md) | <目标语言>`；创作的源语言文件对应对称。
- **结构与对侧镜像**：标题深度与顺序、列表种类、有序列表起点、列表项数、表行列数、语义链接目标（含精确 query/fragment 后缀）、逐字节代码块，一一对应。
## 2. 门禁：verify-translation-pairing
1. 每个在范围内的文档都有完整一对；
2. 每个存在的一对都完整且一致：三文件齐全、两侧当前 blob hash 等于记录值（改任一侧不重录就变红）、切换行存在、结构签名按序匹配；
3. 排除清单里的文件完全没有对侧与记录。
**门禁的界限（原文明说）**：绿门禁只意味着「这对在这些精确内容上确认过一致」，不意味着「确认是可靠的」。它查哈希与结构，无法判断两侧是否真说同一件事——那是评审者的一半契约。**一个重录了但对侧潦草的对能过门禁；它必须过不了评审。**
## 3. 范围与排除
**范围**：所有面向内外读者的人类可读文档 + 决策记录 + 模块 README。**排除**：智能体指令文件（`AGENTS.md`）只用源语言维护；术语表/风格样例结构上就是双语；冻结的归档记录永不重写。
## 4. 术语表
术语表是术语翻译的**唯一权威**，双向绑定。表结构：`English | 目标语言 | 首次出现（带括号注释） | 不要译作（禁止列） | 备注`。通用规则：目标语言列是正文默认用词；首次出现带注释、后续只写括号前部分；「不要译作」是严格禁止译法。**翻译前就加载术语表，而非感到不确定时才查**（「你没注意到的词」最容易漂移）。
---
## 可迁移要点
1. **一对三文件**（双语源 + 目标语言 + 哈希 sidecar），无 locale 目录。
2. **最小更新，绝不整篇重译**。
3. **术语表是唯一权威 + 禁止译法列**。
4. **绿门禁 ≠ 翻译质量**：门禁查哈希 + 结构，评审查「是否真说同一件事」。
5. **智能体指令文件只用源语言维护**——一个明确且实用的取舍。
6. DSH 术语表实例见 `../examples/05-术语表.md`。
